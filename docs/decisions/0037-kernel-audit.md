# 0037: Kernel audit: one append-only log for every module, auth's widened

- **Date:** 2026-11-17
- **Status:** Applied
- **Context:** K3's fifth service (decision 0029). SPEC 6 promised `audit.record(actor, action, target, meta)`, "an append-only audit entry", and SPEC 14.10 described auth's `auth_audit_event`: sign-ins and failures, factor, password and email changes, kept a year, read by staff in full and by each person for their own security activity. Auth had written its own rows since K2 (`kernel/auth/audit.py`), with no reader and no pruning. KICKOFF named VybeSite's `staff_activity` (a closed set of actions, no address in details, rows only ever added) and Basefra.me's `audit/` (filters, newest first) as the sources. `settings.save` carried a `# K3: audit it` marker. The owner approved the contract (`dev plans/contracts/k3-audit.md`) on 2026-11-17 with the four answers recommended.
- **Decision:**
  1. **One table** (the owner's answer): `auth_audit_event` is renamed `kernel_audit_event` by migration `kernel_0008`, keeping its rows, and gains `target_type` and `target_id`, with indexes by actor and by target. Every module writes there, so the staff's log shows "Ana signed in, then changed Ben's roles" in order, one retention rule covers it, and the model lives in `kernel/models.py` (`kernel.auth.models` re-exports it).
  2. **`audit.record(db, action, *, actor, target=, subject=, result="success", details=, request=)`** adds one row to the caller's session and awaits nothing: the change's commit writes it, its rollback drops it. `actor` is required (None is the kernel on its own). It's synchronous, as auth's was; SPEC 6's row changes to say so.
  3. **Names.** An action is `<owner>.<name>`, at most 64 characters: the owner `auth`, `kernel` or an installed module's id, installed by `assemble` as events are. The kernel's actions are a closed set, `audit.KERNEL_ACTIONS`, so a typo is a refusal, and a test holds it equal to the actions the kernel's code passes. A target is `(kind, id)`, the kind named the same way, the id kept as text.
  4. **Details** hold ids, names, counts and flags: JSON values, at most 4 KiB, refusing any string holding `@` and any key with a part naming a secret (`password`, `secret`, `token`, `code`). Every refusal is a ValueError, raised before anything is added. `settings.save` records `kernel.settings_saved` with `{version, changed, via}`: the fields' names, never their values.
  5. **Readers** (the owner's answer): `GET /api/kernel/admin/audit` needs `auth.audit.read` (admins by default) behind the admin gate (a staff role and a second factor), and shows everything, IP addresses included, filtered by actor, subject, action (a name or a prefix ending in a dot), target and time. `GET /api/auth/activity` shows a person their own `auth.*` entries, with `by_you` in place of the actor, so a staff member stays unnamed. Both answer newest first in pages keyed on `(at, id)`. Moderators get a narrower view when moderation is built.
  6. **Retention** (the owner's answer): a year for every entry, `AUDIT_KEEP_DAYS` (at least 30) for a site that wants other. `kernel.prune_audit` runs nightly and deletes past it in batches of 1,000. The general retention service (a later K3 step) takes it over when it lands.
  7. **Append-only in the database** (the owner's answer): a trigger refuses every UPDATE, and every DELETE unless the transaction set `kernel.audit_prune`, which only the pruning does, for its own transaction.
- **Alternatives:** *Auth's table kept for security activity and a second one for the rest:* two readers merged for the staff's page, but each could keep its own retention; the owner chose one. *Keeping the name `auth_audit_event`:* no rename, but every module's rows in an `auth_` table. *Actions declared in module.json:* a manifest field for a filter list K4 can build from the rows; the owner prefix and the kernel's closed set catch what matters now. *An asynchronous `record`:* room for a hash chain later, at the cost of every call site; tamper-proofing is a non-goal. *Code alone keeping it append-only* (VybeSite's way): cheaper, but a bug or a hand-written query could rewrite history.
- **Consequences:** SPEC 6's audit row, 14.10 and 14.11 change, with a change-log line. `kernel.audit` joins the public surface; auth's `record` and `record_by_kernel` are thin wrappers over it; `KERNEL_JOBS` gains `kernel.prune_audit`; `KernelConfig` gains `audit_keep_days`. A deleted person's address and browser stay on their entries until K2 step 11 (deletion) decides otherwise, through the pruning's switch. Role changes, suspensions and module switches record theirs when they're built. Reads aren't recorded; an entry holds no whole objects, so restoring an earlier state reads the owning module's own history.
