# 0036: Kernel events: deliveries are jobs written at emit, so the jobs table is the outbox

- **Date:** 2026-11-17
- **Status:** Applied
- **Context:** K3's fourth service (decision 0029). SPEC 11 described an outbox table, `kernel_event_outbox`, that `events.emit(name, payload)` writes in the caller's transaction, a dispatcher that delivers each row to every `@events.on(name)` handler after commit, retries with backoff, a dead-letter list after 8 failures, and handlers that wait while their module is off. KICKOFF listed "the outbox table, the dispatcher, retries and a dead-letter list". Jobs had just landed with everything a delivery needs (decision 0035): a Postgres queue written in the caller's transaction, `SKIP LOCKED` claims under a lease, backoff, dead jobs, and a module's jobs held while it's off. The owner approved the contract (`dev plans/contracts/k3-events.md`) on 2026-11-17, with the four kernel events whose change existed.
- **Decision:**
  1. **A delivery is a job, written at emit.** `events.emit(db, name, payload)` adds one `kernel_job` per listener to the caller's session, through `jobs.enqueue`, so a delivery exists exactly when the change committed. There is no `kernel_event_outbox` and no dispatcher: the jobs table is the outbox, and the worker that runs jobs runs deliveries. `emit` returns how many it queued; with no listener it writes nothing.
  2. **A listener names its delivery job:** `@events.on(event, "<id>.<name>", timeout=300)` makes an `events.Listener` whose job, of the listener's own module, runs it. So a listener waits while its module is off (the worker claims only the jobs of modules that are on), each listener retries alone, and K4's System page names the listener that failed. The name is explicit, as a job's is, so renaming the function doesn't orphan queued deliveries.
  3. **8 tries, the jobs' backoff:** 30 seconds doubling to an hour, so the 8th try comes about an hour after the first. A delivery dead after them is the dead-letter entry: a dead `kernel_job`, keeping its exception's type name, pruned after 30 days.
  4. **At least once.** A listener MUST be safe to run twice. Every listener and every try sees the same `event.id`.
  5. **Payloads** are `events.Payload` models (frozen, strict, extra fields refused), declared once by their owner with `@events.payload(name, v=1)` in its `events.py`. `emit` takes `db` first and an instance of that name's model; the delivery's payload is the event, `{id, name, v, emitted_at, payload}`, at most 64 KiB, never sealed. A listener reads `event.payload` into the kernel's model or a model of its own (`event.parse(model)`), since modules don't import each other (SPEC 7); `v` is the envelope's, not a payload field.
  6. **Checked at the start.** A module declares only `<id>.*` events (the kernel `auth.*` and `kernel.*`), each once; module.json's `events.emits` and `events.listens` match its `events.py` exactly; a listener to an `auth.*` or `kernel.*` event the kernel doesn't declare, or to an installed module's undeclared event, stops the start. An event of a module that isn't installed may be heard: an optional integration.
  7. **Who hears:** the kernel's listeners and those of the modules `MODULES` allows, switched off or not. A module `MODULES` leaves out gets no deliveries, so none pile up for a module this deploy never runs.
  8. **The kernel emits four events now,** each in its change's transaction: `auth.user.created` (sign-up made an account), `auth.user.verified` (an address confirmed: sign-up's link, a reset that confirmed it, an email change's confirmation), `auth.user.deleted` (`kernel.remove_unverified`, for each account it removes) and `kernel.settings.changed` (`settings.save` with a change: `{module, version}`). SPEC 11's other four are declared by the PRs that build their changes: `auth.user.suspended` with moderation, `auth.user.role_changed` and `kernel.module.enabled` / `disabled` with K4's admin.
  9. **Schemas:** `python -m tools.event_schemas` writes each declared payload as `schema/events/<name>.v<N>.schema.json` (decision 0004) and removes left-over files; `tests/test_event_schemas.py` fails when one is stale.
- **Alternatives:** *SPEC 11's outbox and a dispatcher job:* a second table and a second hop, and a lost wake-up: the dispatcher's job keyed while it runs would swallow an emit landing at its end, so a timed sweep would be needed behind it. What it would add is a log of events nobody hears, and fan-out by the dispatcher's code rather than the emitter's, which matters only during a deploy's overlap, where a new listener misses a few seconds of events it would miss from before its release anyway. *One delivery job per module, named by the kernel:* the System page couldn't say which listener failed, and one module's listeners would share a timeout. *Names derived from the event:* `a.b__c.d` and `a.b.c__d` would collide, and the System page would show `on_auth__user__deleted`. *Handing listeners the emitter's model:* a listener would have to import another module.
- **Consequences:** SPEC 6's events row and section 11 change, with a change-log line. `InstalledModule` gains `payloads` and `listeners`; the harness finds them in `events.py`; `assemble` checks and installs them, so the web app and a worker of its own emit to the same listeners. The tests hear the kernel's events through the `heard` fixture (`kernel/tests/conftest.py`), and K3's gate test is `test_an_event_reaches_its_listener_once_and_a_second_run_changes_nothing`. `kernel.remove_unverified` doesn't run the modules' `delete_user_data` (the export-and-erase hook, decision 0018): its listeners hear `auth.user.deleted`. Wildcard listeners (an outgoing-webhooks module's), version negotiation and requeueing dead letters (K4) are left for later.
