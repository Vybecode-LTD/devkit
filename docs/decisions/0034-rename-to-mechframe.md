# 0034: The project becomes MechFrame, after K3

- **Date:** 2026-11-16
- **Status:** Accepted (the rename itself lands after K3)
- **Context:** "AI DevKit" was a working name. The owner chose **MechFrame**, owns mechfra.me and mechframe.io, has claimed the `@mechframe` npm org, and is claiming `mechframe` on PyPI and GitHub. The name appears about 435 times in 103 files: in prose, and also in the planned CLI (`devkit new`, `devkit add`), the npm and project names (`ai-devkit`, `@devkit/kernel`, `@devkit/harness-web`), the session cookies (`__Host-dk_session`, `__Host-dk_device`), the `DEVKIT_*` variables, the three `devkit-*` project skills and 17 links to `Vybecode-LTD/devkit`.
- **Decision** (the owner's answers, 2026-11-16):
  1. **When:** after K3 is finished, as one mechanical PR, so the kernel services are built and reviewed under one name. Until then new work keeps the DevKit name; no PR mixes the two.
  2. **GitHub:** the owner creates the `mechframe` organization and transfers the repo to github.com/mechframe/mechframe. The rename PR updates every link; GitHub redirects the old ones meanwhile.
  3. **Python:** the import name stays `kernel`. The kernel is copied into each site, not installed (decision 0002), so the import needn't match the PyPI name. PyPI's `mechframe` is the CLI. If the kernel is ever published as a package, its import name is decided then.
  4. **CLI:** `mechframe`, with `mf` as a second name. TeX installs a Metafont program called `mf`; where both are on the PATH, the first one found wins, and `mechframe` always works. The CLI is built in K5, after the rename, so it starts with these names.
  5. **The rest, by the same rule:** npm names `@mechframe/kernel`, `@mechframe/harness-web` and the root `mechframe`; the Python project `mechframe`; cookies `__Host-mf_session` and `__Host-mf_device` (nothing is deployed, so nobody is signed out); `DEVKIT_*` variables become `MECHFRAME_*`; the skills `devkit-module-extractor`, `devkit-site-picker` and `devkit-hook-designer` become `mechframe-*`; prose says MechFrame. Earlier decision records stay as written.
- **Alternatives:** *Rename now:* K3 is mid-way, with PRs open; renaming between services would split the history and every open branch. *Rename the Python package to `mechframe`:* hundreds of import lines across the kernel, modules, tests and migrations, for a package nobody installs yet. *Keep the repo under Vybecode-LTD:* the owner chose the product's own organization. *`mechframe` alone:* the owner wants the short `mf` too.
- **Consequences:** the rename PR changes SPEC (with a change-log line), `CLAUDE.md`, `AGENTS.md`, the docs, the package names, the cookies, the variables, the skills and the links, and runs the full suite and the contract suite. The owner's steps at the same time: transfer the repo, install Codex and CodeRabbit on the new organization (app installs belong to an organization; the ruleset and Actions secrets move with the repo), rename the account's copies of the `devkit-*` skills, and, if they rename `C:\DEV\AI-DevKit`, Claude Code's memory for the project moves with it.
