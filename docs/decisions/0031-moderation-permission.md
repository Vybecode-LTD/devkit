# 0031: The kernel declares `kernel.moderation.act`, and a custom role is staff

- **Date:** 2026-11-16
- **Status:** Applied
- **Context:** The Vibrant Mindz site's step 0 (`docs/plans/vibrant-mindz-backend/kernel-additions.md`, items 1 and 2) asks two things of the kernel before its modules are built. First, moderation is a kernel service (SPEC 6, built in K3), but no permission was declared for acting on reports, and the site's admin designs, `comments` and `community` all name `kernel.moderation.act`. Second, the site seeds a custom `artist` role whose holders must have a second factor; the kernel only has to count custom roles as staff.
- **Decision:**
  1. **`kernel.moderation.act`** is declared in `kernel/kernel.json` ("Act on moderation reports: hide, delete, time out and ban"), with `admin` and `editor` as its default roles, as the designs have it. Migration `kernel_0005` grants it to both; going down removes every grant of it. `KERNEL_PERMISSIONS` holds it, so an owner holds it whatever the roles say. It is declared now, ahead of K3's moderation service, so the modules and the admin can name it from their first build. Who may report is K3's to decide.
  2. **A custom role is staff.** This was already the rule (SPEC 14.1: staff is any role other than `member`) and the code (`sessions._staff_clause`), so nothing changes but the spec's wording, which now says so outright, and a test: `test_access.py::test_a_custom_role_is_staff_and_needs_a_second_factor_too`. The existing admin-gate test used only `editor`, so limiting staff to the built-in roles would have passed every test before this one.
- **Alternatives:** *Rename it in the designs to a module's permission:* moderation is shared by comments, community and any later forum or reviews, so it belongs to the kernel, which owns the service. *Grant it to admin only:* the designs give editors the queue, and a site can take it away from its editors in the roles screen.
- **Consequences:** SPEC.md section 6's moderation row and 14.1 change, with a change-log line. The kernel's manifest gains a permission; the seed test (`test_tables.py::test_the_seeded_grants_are_the_kernel_manifests`) and the manifest test (`test_app.py::test_the_kernels_permissions_match_its_manifest`) hold the seed and the code to it.
- **See:** SPEC.md 6, 14.1 and 14.8; decisions 0013 and 0029; `docs/plans/vibrant-mindz-backend/kernel-additions.md`
