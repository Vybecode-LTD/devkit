# 0035: Kernel jobs: a Postgres queue enqueued in the caller's transaction, at least once, with the worker in the web process by default

- **Date:** 2026-11-16
- **Status:** Applied
- **Context:** K3's third service (decision 0029). SPEC 2 settled a Postgres-backed queue with no broker, and SPEC 6 listed `jobs.enqueue(name, payload, run_at)` and `@jobs.scheduled(cron)`. The kernel's mails went out in `BackgroundTasks` after each answer and weren't retried (decision 0033 left retries to jobs), SPEC 14.7 removes unverified accounts after 7 days, and Vibrant Mindz's track processing needs ffmpeg in a worker (`kernel-additions.md`, item 4). The owner approved the contract (`dev plans/contracts/k3-jobs.md`) on 2026-11-16 and chose where the worker runs.
- **Decision:**
  1. **Enqueued in the caller's transaction:** `jobs.enqueue(db, name, payload, *, run_at, key, sealed)` adds a row to the caller's session, so a job exists exactly when the change it follows committed. That puts `db` first, a change to SPEC 6's signature, as `events.emit` will need too. `key` makes an enqueue a no-op while a job of that name and key is queued or running (a partial unique index), and is free again once it has ended.
  2. **Declared per module, checked at the start:** `@jobs.handler(name, tries=5, timeout=300)` and `@jobs.scheduled(cron, name, tries=1, timeout=300)` make `jobs.Job`s, found in `backend/<id_>/jobs.py` by their type and passed as `InstalledModule(jobs=...)`. Names are `<owner>.<name>`, as mail templates are. `create_app` and `create_worker` refuse to start on another owner's name, a duplicate, a bad cron line, or a scheduled job module.json doesn't list with the same schedule (or the reverse).
  3. **At least once, never exactly once.** Workers claim due jobs with `FOR UPDATE SKIP LOCKED` (Basefra.me's scheduler) under a 60-second lease renewed every 20 seconds; a job whose lease lapsed is claimed again as its next try, and one whose tries ran out that way is dead (`WorkerLost`). Every outcome is written only while the claim's try number still stands, so a try that outlived its lease can't overwrite the one that replaced it. A handler MUST be safe to run twice.
  4. **Outcomes:** returning is done; `Retry(after)` or any exception is queued again after 30 seconds doubling to an hour (±10 %), or `after` (at most a day), until `tries` are used, then dead; `Abandon` is dead at once; a try is cut off at `timeout` (6 hours at most). The row keeps the exception's type name, never its message.
  5. **Payloads** are JSON objects of at most 64 KiB (the mail job's limit is its message's). `sealed=True` stores one through `crypto.seal` and wipes it when the job ends.
  6. **The scheduler** ticks once a minute in each worker under a transaction advisory lock, so one scheduler enqueues each slot once, keyed by the slot, and `kernel_job_schedule` keeps each job's newest slot. Missed slots collapse into one run; none older than 7 days is caught up; a new scheduled job starts from now; a switched-off module's slots wait, and its newest one runs once it's back on. Cron lines are five fields, UTC, parsed by the kernel (`kernel/cron.py`), without names or the `L W # ?` extensions; when both day fields are restricted, either matches, as cron does.
  7. **Where the worker runs** (the owner's choice): in the web process by default (`JOBS_IN_WEB=true`, run by `create_app`'s lifespan: one service), or as a service of its own (`kernel.worker.serve(create_worker(...))`, `python -m app.worker` in a site) with `JOBS_IN_WEB=false` on the web service. Vibrant Mindz runs its own, for ffmpeg. A worker process stops on SIGTERM or SIGINT, gives its running jobs `JOBS_DRAIN_SECONDS` (20) and leaves the rest to their leases; a watchdog thread ends it with status 124 when its event loop stops answering for 2 minutes (both from VybeSite's worker).
  8. **Mail moves onto the queue:** `email.queue(db, template, to, context)` and `email.queue_message(db, to, subject, text, html)` render and check now and enqueue `kernel.send_mail`, sealed, so a sign-in code or reset link is never readable in the jobs table and is wiped once sent. `MailError.retryable` becomes `Retry(retry_after)`, a refusal `Abandon`; 5 tries. Every kernel mail is queued before its route's commit, inside the response-time floor where there is one; `BackgroundTasks` is gone from the kernel.
  9. **The kernel's scheduled jobs:** `kernel.prune_jobs` (daily: done jobs after 7 days, dead after 30) and `kernel.remove_unverified` (hourly: accounts never verified, made over 7 days ago, `active`, with no role but `member`; locked first with `SKIP LOCKED`, so a request holding an account wins; one audit row each, under the id alone).
- **Alternatives:** *A broker (Redis, RQ, Celery, arq):* another service, against SPEC 2. *croniter:* a dependency, and one whose maintenance has wavered, for a parser the scheduler needs only part of. *LISTEN/NOTIFY to wake workers:* a dedicated connection each; polling every second is enough for mail. *Sending in the request and queueing only retries:* a crash between the answer and the send would still lose the mail. *Keeping mail unsealed:* the jobs table would hold live sign-in codes and reset links in plain text, where the kernel keeps only their hashes everywhere else. *The worker always a service of its own:* more cost for sites whose jobs are light. *The worker only in the web process:* ffmpeg would share the web process's CPU.
- **Consequences:** SPEC 6's jobs row and 14.7 change, with a change-log line. The tests run due jobs themselves: no test app runs a worker (`JOBS_IN_WEB=false` in `conftest.py`), the tests' transport (`kernel/tests/conftest.py`'s `Draining`) runs them after each answer, and the harness's `GET /api/_test/mail` runs them before it reads, with `POST /api/_test/jobs/run` for the rest. K3's events dispatcher runs in this worker next; until then a removed unverified account emits no `auth.user.deleted`. K4's System page reads `kernel_job` for dead jobs. The K3 gate's "a job survives a worker restart" is `test_a_killed_worker_s_job_is_finished_by_the_next`: a worker process killed mid-job, its job finished by the next. The site template's worker service and Dockerfile arrive with K5.
