# 0028: Passkeys: registration, sign-in alone or as a second factor, step-up, list, rename and removal

- **Date:** 2026-11-16
- **Status:** Applied
- **Context:** SPEC 14.2 makes passkeys every account's preferred sign-in method ("the `webauthn` library, discoverable credentials, and user verification required when the passkey is the only factor"), and 14.4 counts them as a second factor. The contract had only `POST /passkeys/register/start` (step-up; 403 until the address is verified), `/register/finish` (201) and `DELETE /passkeys/{id}` (step-up; 204): nothing to sign in with a passkey, alone or after a password, nothing to step up with one (an account with only passkeys has no password to step up by), and no way for a client to learn a passkey's id. The owner chose the shape on 2026-11-16.
- **Decision:**
  - **Ceremonies.** Options come from `webauthn` (3.0). Each challenge is 32 random bytes, kept only as a keyed hash in `auth_token` (decision 0012), valid 5 minutes and used once: purposes `passkey_register`, `passkey_sign_in` and `passkey_step_up` (migration `kernel_0003`), and, for a second factor, beside the sign-in's challenge. The relying party is the host of `SITE_URL` and the expected origin is its origin; with DEBUG on, `CORS_ORIGINS` count too, as they do for the same-origin check. Attestation is `none`; EdDSA, ES256 and RS256 are accepted.
  - **Registration.** `register/start {name}` (step-up, a verified address) answers creation options that ask for a discoverable credential and user verification, exclude the account's passkeys and name the account by its address, with its id (16 bytes, nothing personal) as the user handle. The challenge is bound to the session that asked. The name is 1 to 80 characters once trimmed. An account holds at most 20 passkeys (409 `auth.too_many_passkeys`), a bound of ours. `register/finish` takes the browser's credential as the body, checks everything again with the account held (the address still verified, the session still live, the count) and verifies with user verification required: 201 `{id, name, created_at, last_used_at}`, a security mail and an audit row; 400 `auth.invalid_passkey` for a credential that doesn't verify, a challenge used, expired or another session's, or a credential already registered.
  - **Signing in with a passkey alone** (the owner's answer: everyone, staff included). `POST /passkeys/sign-in/start` answers request options with no `allowCredentials` (the authenticator offers its own discoverable passkeys) and user verification required; `POST /passkeys/sign-in/finish` takes the credential and answers as sign-in does, `{"status": "signed_in", "user"}` with the cookie. A verified passkey is two factors (something held, unlocked by something known or a body), so there is no second-factor step after it, and the session counts as having passed one. Anything wrong (an unknown or used challenge, an unknown credential, a user handle that isn't the passkey's account, a missing user verification, a bad signature, a sign count that went back, an account that can't sign in) answers the same 401 `auth.invalid_passkey`. Each route takes 10 per IP per minute.
  - **A passkey as the second factor** (the owner's answer: a start route). `POST /sign-in/second-factor/passkey {challenge}` answers request options for that account's passkeys, user verification preferred, and keeps the WebAuthn challenge on the sign-in's challenge, each call replacing the last; it costs no try. 401 `auth.challenge_ended` as the second-factor step answers; 409 `auth.no_passkey` for an account with none. The existing `POST /sign-in/second-factor` then takes `{challenge, passkey}`, within the same 5 tries per sign-in and 10 failures per account an hour; a wrong one answers 401 `auth.invalid_second_factor`.
  - **Step-up by passkey**, the same way. `POST /step-up/passkey` answers request options for the account's passkeys, user verification required (for an account with only passkeys it is the only factor), its challenge bound to the session; 409 `auth.no_passkey`. `POST /step-up {passkey}` then steps up as a password or a TOTP does; a wrong one answers 401 `auth.invalid_passkey` and counts as a failed step-up, so the fifth ends the session.
  - **The list and renaming** (the owner's answer). `GET /passkeys` answers `{"items": [{id, name, created_at, last_used_at}]}`, oldest first. `PATCH /passkeys/{id} {name}` (step-up) renames one: 200 with it, an audit row and no mail, since a name opens nothing.
  - **Every removal is a second-factor reset** (the owner's answer). `DELETE /passkeys/{id}` (step-up) deletes the passkey, raises the session epoch so every other session ends, keeps this one at the new epoch with a fresh device cookie, voids every live sign-in code and link, reset link and second-factor challenge, and mails the account, as removing a TOTP does (decision 0027), whether or not other factors remain. 404 `auth.passkey_not_found` for an id that isn't one of the account's. Removing the last passkey of an account with no password is allowed: a member signs in by email code, and anyone can reset.
  - **Sign counts.** A count that doesn't rise, when either the stored count or the new one isn't zero, is refused as a cloned authenticator; synced passkeys always report zero. Every use stores the count and `last_used_at`.
  - **One lock order** (decisions 0021 and 0027): every route that reads a passkey to change it or writes an account's token, session or passkey rows locks the account first. A challenge with no account yet (`passkey_sign_in`) is used up before the account is locked.
  - **Audit:** `auth.passkey_added`, `auth.passkey_renamed`, `auth.passkey_removed`, and `auth.sign_in`, `auth.second_factor` and `auth.step_up` with method `passkey`.
- **Alternatives:**
  - *Members only for a passkey alone*, staff giving a password first. A staff member's passkey is their second factor already; asking for a password as well adds a phishable secret to the strongest method.
  - *Put the WebAuthn options in the second-factor answer.* One round trip fewer, but every such sign-in would mint a challenge even when the person then types a TOTP.
  - *End other sessions only when the last factor goes, or never.* The owner chose every removal: whoever stole a session can't remove the owner's passkey and keep the rest of their sessions.
  - *Ask for an email before a passkey sign-in.* It would say which addresses hold passkeys, and discoverable credentials make it unnecessary.
  - *Key the second-factor WebAuthn challenge as its own token.* Keeping it on the sign-in's challenge reuses its tries, its expiry and its account budget.
- **Consequences:**
  - SPEC.md 14.2, 14.4, 14.5 and 14.6 say so, with a change-log line; `docs/contracts/auth-api.md` gains the rows. `kernel/backend/kernel/auth/passkeys.py` holds the routes; migration `kernel_0003` adds the three token purposes.
  - The contract suite's passkey cases of `test_an_unverified_account_adds_no_second_factor` and the step-up list now run, with the passkey tests; it drives a software authenticator (`kernel/tests/contract/authenticator.py`) that speaks only WebAuthn's wire format, so a port passes the same suite.
  - A site's sign-in page offers the passkey first (14.2, K4).
